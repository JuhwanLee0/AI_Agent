## 1. Five-Axis Code Review & Quality (5개 축 코드 품질 리뷰)
> **"사원B(백엔드)와 사원C(프론트엔드)가 제출한 모든 코드는 머지 및 배포 전 아래 5개 축을 전수 통과해야 한다."**

### 5개 축 평가 기준
1. **정확성 (Correctness)**: 
   - 스펙 문서(PRD)의 요구사항과 완전히 일치하는가?
   - Null/Empty/경계값 및 에러 처리 경로가 누락 없이 작성되었는가?
   - 테스트 코드가 정상 동작을 실제로 증명(Proof)하는가?
2. **가독성 & 단순성 (Readability & Simplicity)**:
   - 100줄로 끝낼 수 있는 로직을 500줄로 장황하게 늘려 쓰지 않았는가?
   - 변수/함수명이 명확하고 컨벤션을 준수하는가?
   - 불필요한 추상화나 미사용 코드(`_unused`)가 없는가?
3. **아키텍처 (Architecture)**:
   - 모듈 간 경계가 깔끔하고 순환 참조가 없는가?
   - 타입 경계(`Pydantic/TypeScript`)가 명시적인가?
4. **보안 (Security)**:
   - 시크릿 키 하드코딩 없음, RLS 정책 활성화, SQL 인젝션 차단 확인.
   - 외부 입력 데이터 검증 및 XSS/CSRF 방어 확인.
5. **성능 (Performance)**:
   - N+1 쿼리 없음, 무한 루프 없음, 불필요한 렌더링/메모리 누수 없음.

### 리뷰 피드백 태그 규정
- `[Blocking]`: 즉시 수정해야 하는 결함 (수정 전까지 다음 단계 진행 불가).
- `[Optional]`: 개선하면 좋으나 배포를 막지는 않는 제안.
- `[Nit]`: 사소한 스타일/오타 교정.

## 2. Security Penetration & Vulnerability Testing (모의 침투 점검)
> **"해커의 시각으로 코드를 공격하여 사전에 구멍을 뚫고 메운다."**

### 모의 침투 4대 점검 리스트
1. **인증 우회 공격**: 헤더/쿠키 변조, 토큰 만료 후 요청, 타인 user_id로의 리소스 접근 시도 (IDOR 취약점).
2. **권한 상승(Privilege Escalation)**: 일반 유저 토큰으로 Admin 엔드포인트 호출 시도.
3. **인젝션 공격**: 인풋 폼 및 쿼리 파라미터에 특수문자, 따옴표, `<script>` 태그 주입.
4. **결제 금액 변조**: 클라이언트 요청 바디의 결제 금액(`amount`)을 0원이나 음수로 조작하여 전송.

---

## 3. Flawless Rejection Protocol (반려 규정)
- 단순히 "안 됩니다"라는 모호한 피드백을 엄격히 금지합니다.
- 반드시 **[1] 문제가 발생한 파일과 정확한 라인 번호**, **[2] 실패를 유발한 입력 데이터/재현 절차**, **[3] 권장되는 구체적 수정 코드 예시**를 명시하여 사원B/C에게 명확히 반려(Reject)합니다.
